Functional Requirements Document
DeQueue ΓÇô Role-Based Access Control & Order Workflow Authorization
1. Document Overview
Project: DeQueue
Feature: Dynamic Role-Based Access Control (RBAC) and Order Workflow Authorization
Platform: Web/Admin, Android and Backend
Primary Users: DeQueue Platform Admin, Vendor Admin and Vendor Staff
2. Objective
Allow DeQueue to centrally define the available permissions.
Allow each vendor to create custom roles by combining predefined permissions.
Allow vendors to assign one or more roles to staff.
Control application features and actions based on effective permissions.
Control order visibility based on role and allowed order statuses.
Allow order actions only when the user has the required permission and the order is in a valid state.
Maintain strict vendor-level tenant isolation.
Provide Android clients with effective permissions for dynamic UI rendering.
Keep the backend as the final source of truth for authorization.
3. User Hierarchy
DeQueue operates with two authorization scopes: Platform and Vendor. The Platform Admin manages vendors, while the Vendor Admin manages users, roles, departments and vendor operations within that vendor.
DeQueue Platform ΓåÆ Platform Admin ΓåÆ Vendor ΓåÆ Vendor Admin ΓåÆ Roles / Departments / Staff
4. Platform Admin
Create, view, update, activate and deactivate vendors.
Manage platform-level configuration.
Define and maintain the global permission catalog.
Operate independently of vendor-specific roles.
5. Vendor Admin
Manage vendor-specific staff.
Create, update and delete vendor roles subject to system restrictions.
Assign roles to staff.
Manage departments.
Manage vendor operations such as orders, menu and reports according to permissions.
Access only data belonging to the vendor.
6. Permission Model
Permissions are defined and maintained by DeQueue. Vendors cannot create arbitrary permissions. Permissions represent capabilities that the application exposes.
7. Role Management
Roles are vendor-owned configurations. A vendor can create any number of roles and combine the predefined DeQueue permissions according to its operational needs.
Examples:
Kitchen Staff: order.view, order.prepare, order.ready
Kitchen Manager: order.view, order.accept, order.prepare, order.ready, order.complete, order.cancel, menu.view, menu.update, staff.view
Counter Staff: order.view, order.complete
8. Staff and Role Assignment
A staff member may be assigned one or more roles. Effective permissions are the union of permissions granted by all assigned roles.
Example: Rahul ΓåÆ Kitchen Staff + Inventory Manager ΓåÆ effective permissions include order.view, order.prepare, order.ready, inventory.view and inventory.update.
9. Departments
Departments and roles are separate concepts. A department identifies an operational area, while a role determines what the staff member is allowed to do.
Example: Rahul ΓåÆ Department: Kitchen; Role: Kitchen Manager.
10. Order Workflow
The order lifecycle is controlled by a predefined state machine:
PENDING ΓåÆ ACCEPTED ΓåÆ PREPARING ΓåÆ READY ΓåÆ COMPLETED
Optional cancellation transitions may include PENDING ΓåÆ CANCELLED, ACCEPTED ΓåÆ CANCELLED and PREPARING ΓåÆ CANCELLED.
The valid order state machine is controlled by DeQueue and cannot be arbitrarily modified by vendors.
11. Order Action Authorization
Every order action requires both the required permission and a valid current order state.
12. Order Visibility
Order visibility is separate from action permissions. A role may have order.view while still being restricted to specific order statuses.
13. Backend Authorization Flow
For every protected request the backend must validate: authentication ΓåÆ vendor/tenant isolation ΓåÆ permission ΓåÆ resource visibility ΓåÆ workflow state transition.
Example for POST /orders/{id}/prepare: validate JWT, verify the order belongs to the user's vendor, verify order.prepare permission, verify the order is visible, verify current status is ACCEPTED, then transition it to PREPARING.
14. Tenant Isolation
All vendor-owned resources must be scoped by vendorId. A user belonging to Vendor A must not be able to access or modify Vendor B data, even if the user has the relevant functional permission.

15. Android Application Requirements
After login, the backend shall provide the user's effective permissions. The Android application shall use these permissions to control navigation, screens, buttons and available actions.
Example: order.prepare ΓåÆ display Start Preparing; order.ready ΓåÆ display Mark Ready; order.complete ΓåÆ display Complete.
Android UI restrictions are for user experience only. They must never replace backend authorization.
16. Login and Session Requirements
During login, the backend determines the user, vendor, assigned roles and effective permissions. The access token/session may contain vendorId, user identity, role IDs and permissions. Access tokens should be short-lived so permission changes become effective promptly.
17. Redis and WebSocket Integration
Successful order state changes shall update MongoDB, record status history, update relevant Redis state and publish a real-time event through the existing WebSocket/pub-sub mechanism.
Example: Vendor accepts PENDING ΓåÆ ACCEPTED ΓåÆ MongoDB update ΓåÆ status history ΓåÆ Redis update ΓåÆ ORDER_ACCEPTED event ΓåÆ Kitchen Android displays the order.

20. Audit Requirements
Every successful order status transition must record the previous status, new status, user/staff ID and timestamp in the order status history. Role and permission changes should also be auditable through the existing audit_logs mechanism.
21. Functional Requirements
22. End-to-End Example
Platform Admin creates Pizza Palace and its initial Vendor Admin.
Vendor Admin creates Kitchen Staff with order.view, order.prepare and order.ready.
Vendor Admin configures Kitchen Staff visibility as ACCEPTED, PREPARING and READY.
Vendor Admin creates Counter Staff with order.view and order.complete, visible only for READY orders.
Customer places an order; status is PENDING. Vendor Admin sees it; Kitchen Staff does not.
Vendor accepts the order; status becomes ACCEPTED and a real-time event makes it visible to Kitchen Staff.
Kitchen Staff starts preparation; status becomes PREPARING.
Kitchen Staff marks the order ready; status becomes READY.
Counter Staff sees the READY order and completes it; status becomes COMPLETED.
Each successful transition is stored in status history and propagated through Redis/WebSocket.
23. Key Design Principles
DeQueue defines permissions; vendors define roles.
A role is a combination of predefined permissions.
Departments represent operational grouping, not authorization.
The order state machine is controlled by DeQueue.
Vendors control which roles can perform valid actions.
Order visibility is separate from action permission.
Every request must satisfy authentication, tenant isolation, permission and workflow checks.
Android controls the user experience; backend controls security.
Vendor-specific configuration must never compromise cross-tenant isolation.
